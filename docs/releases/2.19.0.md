# Bazis 2.19.0

## Fixed

- **A schema error with its own context failed with a `TypeError` (up to 2.18.0).**
  `model_validate` rebuilt the errors of a schema with `ValidationError.from_exception_data`,
  which makes a built-in error type only from the context it was created with. The errors
  of `EmailStr` (type `value_error` without `ctx['error']`) made it raise
  `TypeError: 'error' required in context`: a list with a stored email such as
  `smoke@example.test` answered 500, and so did a request that sent it. The errors are
  rebuilt as custom errors that keep the type, the message and the context: the client gets
  422 `ERR_VALIDATE` with the message and the pointer, as for any other schema error.
- **`route_filter_fields/` with a relation to a route set without a list (up to 2.18.0).**
  The endpoint looked up the list route of the route set of every related model and
  answered 500 when that route set is registered without `action_list` (for example
  `as_router(actions=['action_create', 'action_retrieve'])` for a file upload). Such a
  relation is now listed with the `py_type` `unknown`, as a relation to a model without a
  route. A project that kept an empty list on a route set only to avoid the error can drop
  it.
- **The discovery of `conf.py` imported the other subpackages (up to 2.18.0).** While the
  settings are built, `conf_modules()` imported the `__init__` of every subpackage under
  `bazis.contrib` (and of the project) to look for `conf.py` modules. An `__init__` that
  imports models or `bazis.core` broke the settings (GDAL errors, Django reporting only
  "Unknown command"), so such a package, like `bazis.contrib.front.contract`, had to keep
  its `__init__` empty. The subpackages are now found by their paths
  (`walk_packages_excluding` takes the search path of a subpackage from its finder), and
  only the `conf.py` modules, with the packages they sit in, are imported. The modules found
  and their order are the same; nested modules such as
  `bazis.contrib.authing.services.google.conf` are still found.

## Added

- **The cookies of a `JsonApiBazisException` take their attributes.** A cookie of the
  exception can be a `bazis.core.errors.JsonApiCookie(key, value, max_age, httponly=False,
  secure=False, samesite='lax', path='/')`, and the error response of the application sets
  it with those attributes:

  ```python
  raise JsonApiBazisException(
      errors,
      cookies=[JsonApiCookie('auth', token, 3600, httponly=True, secure=True)],
  )
  ```

  A plain `(key, value, max_age)` tuple still works and sets the same cookie as before (the
  defaults of `JsonApiCookie` are those of Starlette's `set_cookie`: path `/`, SameSite
  `lax`, neither `HttpOnly` nor `Secure`). A package that set the attributes on the error
  response itself (calling the exception handler of the application and `set_cookie` on its
  response) raises the exception with a `JsonApiCookie` instead. bazis-authing 2.8 relies on
  it for the cookie of its store.

## Upgrading

- `walk_packages_excluding` no longer imports the packages it walks, so it has no `onerror`
  argument (nothing is imported to fail). A caller that passed it must drop it.
