# Bazis 2.19.0

## Fixed

- **A schema error with its own context failed with a `TypeError` (up to 2.18.0).**
  `model_validate` rebuilt the errors of a schema with `ValidationError.from_exception_data`,
  which makes a built-in error type only from the context it was created with. The errors
  of `EmailStr` (type `value_error` without `ctx['error']`) made it raise
  `TypeError: 'error' required in context`: a list with a stored email such as
  `smoke@example.test` answered 500, and so did a request that sent it. The errors are
  rebuilt as custom errors that keep the type, the message and the context: the client gets
  422 `ERR_VALIDATE` with the message and the pointer, as for any other schema error.
- **`route_filter_fields/` with a relation to a route set without a list (up to 2.18.0).**
  The endpoint looked up the list route of the route set of every related model and
  answered 500 when that route set is registered without `action_list` (for example
  `as_router(actions=['action_create', 'action_retrieve'])` for a file upload). Such a
  relation is now listed with the `py_type` `unknown`, as a relation to a model without a
  route. A project that kept an empty list on a route set only to avoid the error can drop
  it.
- **The discovery of `conf.py` imported the other subpackages (up to 2.18.0).** While the
  settings are built, `conf_modules()` imported the `__init__` of every subpackage under
  `bazis.contrib` (and of the project) to look for `conf.py` modules. An `__init__` that
  imports models or `bazis.core` broke the settings (GDAL errors, Django reporting only
  "Unknown command"), so such a package, like `bazis.contrib.front.contract`, had to keep
  its `__init__` empty. The subpackages are now found by their paths
  (`walk_packages_excluding` takes the search path of a subpackage from its finder), and
  only the `conf.py` modules, with the packages they sit in, are imported. The modules found
  and their order are the same; nested modules such as
  `bazis.contrib.authing.services.google.conf` are still found.

## Added

- **The cookies of a `JsonApiBazisException` take their attributes.** A cookie of the
  exception can be a `bazis.core.errors.JsonApiCookie(key, value, max_age, httponly=False,
  secure=False, samesite='lax', path='/')`, and the error response of the application sets
  it with those attributes:

  ```python
  raise JsonApiBazisException(
      errors,
      cookies=[JsonApiCookie('auth', token, 3600, httponly=True, secure=True)],
  )
  ```

  A plain `(key, value, max_age)` tuple still works and sets the same cookie as before (the
  defaults of `JsonApiCookie` are those of Starlette's `set_cookie`: path `/`, SameSite
  `lax`, neither `HttpOnly` nor `Secure`). A package that set the attributes on the error
  response itself (calling the exception handler of the application and `set_cookie` on its
  response) raises the exception with a `JsonApiCookie` instead. bazis-authing 2.8 relies on
  it for the cookie of its store.

## Changed

- **The `conf.py` of the project overrides the defaults of the core and of the packages.**
  The `conf.py` modules are merged into one settings class, and the default of a setting
  declared in several of them comes from the first one. The project came last, so a setting
  of the core or of a package that the project redeclared with another default kept the
  default of the core or of the package, silently. The order is now: the project, the core,
  the packages. A `BS_<NAME>` variable still wins over every default; of the packages listed
  in `BS_BAZIS_APPS` the last one still wins. The core keeps its priority over the packages:
  an old release of a package that still redeclares a Django setting (`AUTH_USER_MODEL` of
  bazis-users before 2.5) does not change it. No package declares a setting of the core.
- **The identifiers of a relationship by a foreign key with `to_field` are primary keys.**
  Since 2.11.0 the `id` of such an identifier was the value of the referenced field
  (`to_field`), while the resource of the related object in `included`, its URL and every
  other identifier of the API use its primary key: a client could not match the
  identifier with the included resource, and the checks that look the related object up
  (`relations_access_check`, the relationships endpoints) looked it up by the primary key
  too, so a value that has the format of a primary key (a UUID `to_field`) inspected
  another object: a false 403 `ERR_RELATION_ACCESS`, or a hidden or not linkable object
  linked. Now `relationships.<field>.data.id`, `included[].id` and the id in
  `/<prefix>/<id>/` are the same primary key for every relationship, and the value of the
  `to_field` stays in the column of the foreign key:
  - a read gives the primary key of the related object (the queryset of the route annotates
    it, `RelationInfo.related_pk` looks it up for an object loaded otherwise);
  - a write (create, update, the relationships endpoints) takes the primary key and stores
    the value of the `to_field` of that object (`RelationInfo.fk_value`); the checks of the
    targets are those of the other relations, by the primary key;
  - the filter by the relation (`filter=<field>=<pk>`, `<field>__in`), the filter by the id
    of a related object (`filter=<type>=<id>`), the sorting by the relation and the
    `group=<field>` of `meta=aggregates` work with primary keys; the subqueries of the
    relation (filter, sort and search through it) compare the foreign key with the
    referenced field.
- `RelationInfo.key_field` is the field a relation references (the primary key, or the
  `to_field`).

## Upgrading

- `walk_packages_excluding` no longer imports the packages it walks, so it has no `onerror`
  argument (nothing is imported to fail). A caller that passed it must drop it.
- A setting that the `conf.py` of a project redeclares with its own default now takes that
  default. Check the `conf.py` of the projects for settings of the core or of the packages
  redeclared by accident (`DEBUG`, `ALLOWED_HOSTS`, `BAZIS_*`): those defaults were ignored
  before and apply now.
- A client that sent or read the value of a `to_field` as the id of a relationship must use
  the primary key of the related object now: the value of the field is not an identifier
  (422 `ERR_VALIDATE` if it is not a primary key; another object if it has the format of
  one).
