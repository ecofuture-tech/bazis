# Bazis 2.8.0

The schemas and the OpenAPI follow the language of each request. Breaking: the default
`LANGUAGE_CODE` is `en`, and `/openapi.json` is in the language of the request.

## Features

- **The language of a request** (`LanguageMiddleware`, `bazis.core.i18n.request_language`)
  is the query parameter `lang`, otherwise the languages of the header `Accept-Language`
  by their weight (`q`), the first one of `LANGUAGES`, otherwise `LANGUAGE_CODE`. A code
  matches a language of `LANGUAGES` by itself or by its base code, case-insensitively:
  `ru-RU`, `ru_RU` and `RU` are `ru`. Before, only the first language of the header was
  read and it had to be written exactly as in `LANGUAGES`: a browser sending
  `ru-RU,ru;q=0.9` got `LANGUAGE_CODE`, and so did an unknown `?lang` even with a known
  header language.
- **`bazis_doctor` checks the translations**: `bazis.W004`, two Bazis packages translate a
  msgid differently (the first in `LOCALE_PATHS` wins; a msgid the project translates in
  its own `locale` is not reported); `bazis.W005`, a language of `LANGUAGES` other than
  English in which no catalog translates texts of an installed Bazis package (they stay in
  English).

## Fixes

- **The titles of the schemas were in the language of the first request of the process.**
  The schemas are cached once per process, and their titles and descriptions were made
  strings when a schema was built: the `schema_*` routes and the OpenAPI kept the language
  of whatever request built a schema first. The titles and descriptions now stay lazy in
  the cached schemas, as the choice labels (`enumDict`) already did, and are translated
  when a JSON schema is generated, in the active language. In `LANGUAGE_CODE` the OpenAPI
  is the same as before, byte for byte.
- **The default `LANGUAGE_CODE` is `en`** (it was `en-EN`, which is not a language of the
  default `LANGUAGES`): outside the requests (commands, background tasks) the active
  language was `en-en`, the translated fields looked for columns `_en_en` and
  `schemas_build_lang` wrote `schemas_en-en.json`. The language activated by default for a
  request is the language of `LANGUAGES` that `LANGUAGE_CODE` matches (`en` of `en-EN`),
  as before.

## Changes

- **`/openapi.json` (`app.openapi()`) is served in the language of the request**
  (`?lang`, `Accept-Language`, otherwise `LANGUAGE_CODE`), built once per language. Before
  it was in the language of its first request. A code generator that fetches it gets a
  deterministic document by passing `?lang=` or by sending no `Accept-Language` (then it
  is in `LANGUAGE_CODE`; HTTP libraries send none, browsers do). Resetting
  `app.openapi_schema` to None still builds it again. Export a contract in the process
  under `translation.override(settings.LANGUAGE_CODE)` (bazis-front does);
  `schemas_build_lang` writes the language it runs in.
- **Every HTTP response has `Vary: Accept-Language`** (added by `LanguageMiddleware`, as the
  LocaleMiddleware of Django does): the schemas, the OpenAPI, the errors and the translated
  fields depend on it, so an HTTP cache keeps one copy per language.
- A title made a `str` before it reaches the schema (`str(_('Name'))`, an f-string) is
  fixed in the language active then; keep titles lazy (`gettext_lazy`, `verbose_name`).
- In tests, setting `LANGUAGES`, `LANGUAGE_CODE` or `LOCALE_PATHS` with the `settings`
  fixture of pytest-django or `override_settings` makes Django replace the per-request
  translations of the core with thread-local ones (routes run in the thread pool then
  answer in `LANGUAGE_CODE`); set them with `monkeypatch.setattr(settings, ...)`.

## Upgrading

- A project that relied on the default `LANGUAGE_CODE` `en-EN` gets `en`; set
  `BS_LANGUAGE_CODE` to keep another one.
- A client that needs the OpenAPI in one language whatever the user sends asks for it with
  `?lang=` or `Accept-Language`, or exports it in the process under
  `translation.override`.
