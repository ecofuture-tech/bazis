# Bazis 2.20.0

## Features

- **A route without `search_fields` searches the text fields of its LIST schema.** Since
  2.9.0 `search=` (and `$search` of `filter`, also through a relation,
  `customer__$search=`) on a route that does not declare `search_fields` answered 400
  `ERR_FILTER` "The search is not available for ...". Such a route now searches the text
  fields of its LIST schema for the user of the request (`query_fields`, which
  bazis-permit narrows per user), in the order of the schema:
  - a `CharField` or a `TextField` of the model (also `SlugField`, `EmailField`,
    `URLField`) without choices;
  - a `TranslatedField` of such a field, in the language of the request (as with
    `search_fields = ['name']`).

  Not searched: the relations (declare `tag__name` to search through one), the calculated
  fields, the fields with choices (their codes are not text: filter them with
  `filter=status=`), the numbers, the UUID, file, JSON and array fields, the primary key.
  The words, the lookups and the special characters work as with declared fields: every
  word in one of the fields, a substring in any case (`icontains`), `%`, `_` and the
  metacharacters of a regex are literal. The search reaches nothing the route does not
  show: a field the LIST schema hides from the user (a projection with `fields`, the
  field permissions of bazis-permit) is not searched, as it is not a filter key either.
  A route without such fields for the user (an anonymous user without roles of
  bazis-permit) still answers 400.
- **`JsonapiRouteBase.filter_keys_ignored`: filter keys a route leaves out.** Since 2.5.0
  a key of `filter=` naming a field the route does not have is 400 `ERR_FILTER`; before
  it added no condition. A client released against an earlier version that sends one (a
  route of the items of a container filtered by `dt_deleted=null`, which only the
  container has) fails on every such request. `filter_keys_ignored = frozenset({'dt_deleted'})`
  of the route leaves out every key of the `filter` of its requests whose first name is in
  the set, whatever its lookup, value and negation (`dt_deleted=null`,
  `dt_deleted__gt=...`, `~dt_deleted=...`); in an `or` the key is left out as well, not
  taken as true. Only the keys of the route itself: after a relation
  (`capsule__dt_deleted=null` on a route of a model related to it), on another route of
  the model and in the conditions of the code (the permissions of bazis-permit, `filter:`
  restrictions) the key is an unknown field as before (400 `ERR_FILTER` in a request). A key that is a filter key of the route (a field
  of its LIST schema, `id`/`pk`, a filters alias) is the error `bazis.E002` of the system
  checks, and the keys are not in `route_filter_fields/`. Declare it only for the
  compatibility with released clients, never in place of a field to filter by.

## Fixes

- **Choices of a field whose type makes an object of a code (2.18.0 to 2.19.1).** The
  check of the choices compared the `enum` of the field only with the value the schema
  type had made of the request. A field whose type in `TYPES_DJANGO_TO_SCHEMA` makes an
  object of a code (a `CharField` subclass with choices whose type turns `'en'` into a
  language object) refused every value, also a valid one, with 422 `ERR_VALIDATE` "Value
  ... is not a valid choice". A value is now a choice if it is a key as the request sends
  it, as the type converts it (as in 2.18: `"2"` of an integer field, a Decimal, UUID or
  date key sent as the OpenAPI shows it), or if it matches a key converted by the same
  type. Null and empty values are left to the checks of `null` and `blank`, as before.
- **An invalid attribute of a document with `id` but without `type` answered 500.** The
  `type` of `data` may be left out (the schema of the route has it by default), but when
  an attribute of such a document did not validate, the error was built with
  `value['type']` and failed with a `KeyError`. It is now 422 `ERR_VALIDATE` at the
  attribute, its `source` names the item by its `id`. A valid document without `type` is
  written as before.

## Changes

- On a field with choices, a value its type refuses (`"abc"` of an integer field) and a
  text of only whitespace of a field without `blank=True` get the error of the choices,
  "Value ... is not a valid choice", instead of the one of the type or of the blank
  check: still one 422 `ERR_VALIDATE` at the field.
- `search_fields = None` (not declared) and `search_fields = []` are no longer the same:
  `[]` turns the search off (400 `ERR_FILTER`, as before for both), `None` is the default
  above. A declared list works as before (`bazis.W007` for a field out of the schema).
- The search fields of a request live in `QueryScope.search_fields`:
  `QueryScope.for_route` gives the declared fields or the default
  (`bazis.core.utils.query_complex.default_search_fields(model, fields)`), and
  `ServiceSearching`, `SearchToOrm(model, search, scope=scope)` without `search_fields`
  and `$search` of `filter` take them from the scope. Without a scope (`scope=None`) the
  search is unchanged: the declared fields, else every text and integer field of the
  model.
- `route_search_fields(route_cls)` lists the fields a route searches, declared or by
  default (of the LIST schema of the class), so the contract of bazis-front shows the
  search of the routes without `search_fields`.

## Upgrading

- A route that must not be searched declares `search_fields = []`; one with a large list
  declares the fields to search (a substring search uses no btree index, whether the
  fields are declared or not; add a `pg_trgm` index if needed).
- A client that relied on the 400 of `search=` on a route without `search_fields` gets the
  results of the search now.
- A route class that set `search_fields` from its parent's value expecting a list (the
  core no longer replaces `None` by `[]` in `cls_init`) must handle `None`.
- Requires no new version of the dependencies. bazis-front takes the search of its
  resources from `route_search_fields`: regenerate the contract.
