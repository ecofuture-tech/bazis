# Bazis 2.7.0

## Security

- **A relationship links and includes only the objects the user can see.** A client could
  link an object it cannot see (a foreign key or a many-to-many relation set on create or
  update, or through the relationships endpoints) and then read it through `include`: the
  core checked the targets only against the `filter:` restrictions of the field. Now the
  default route of the related model decides, with its `restrict_queryset` for the user of
  the request:
  - create, update and the relationships endpoints (`JsonapiRouteBase.relations_access_check`,
    before the `filter:` restrictions and the hooks) link only the objects it returns for
    `view`; a reverse relationship links and unlinks only the objects it returns for
    `change` (their foreign key changes). Only the objects whose link changes are checked:
    an object linked before stays linked and can be unlinked. Otherwise the request fails
    with 403 `ERR_RELATION_ACCESS` and the pointer `/data/relationships/<field>` (the error
    of bazis-permit);
  - `included` shows only the objects it returns for `view`; the relationships keep the
    identifiers of all linked objects.

  The models whose default route does not override `restrict_queryset`, or that have no
  route, are not checked and cost no extra query; a restricted relationship costs one
  query (and one for the current value of a to-many relationship of a changed item).

## Breaking changes

- **`restrict_queryset` is called by the core** on the default route of the related model,
  as a classmethod with `user` (None without bazis-users) and `route` (the route of the
  request). An override must accept `**kwargs`. Restrict the objects a user must not see
  there, not only in `get_queryset` (which restricts only the route's own list and item).
  bazis-permit 2.4.1 and earlier declare `PermitRouteBase.restrict_queryset` without
  `**kwargs`: a response that includes objects of a permission-protected model fails with
  `TypeError` until bazis-permit is upgraded to the release that accepts them.
  `relations_view_check = False` turns the check off for the relationships of a route.
- **The default route of a model can be declared**: `default_route = True` in the body of a
  route class (not inherited) keeps it the default route of the model whatever route
  classes of the model are defined after it. Without it the last defined route class is
  the default one, as before; abstract route classes never are.

## Features

- **New check `bazis.W003`**: a model is served by several route sets and not one of them
  declares `default_route = True`, so the import order decides which one restricts the
  objects of the model in the other routes.
- **The application serves the media and the static files in development.** `MEDIA_URL` is
  still redirected to `MEDIA_HOST_URL` (else `ADMIN_HOST_URL`) and `STATIC_URL` to
  `ADMIN_HOST_URL`. Without such a host the redirect pointed at the application itself and
  looped; now, in DEBUG, the application serves the files from `MEDIA_ROOT` /
  `STATIC_ROOT` (a project no longer mounts them by hand). The media are the files the
  clients upload, so they are sent with `X-Content-Type-Options: nosniff`, `Content-
  Security-Policy: sandbox` and, unless they are raster images, `Content-Disposition:
  attachment`. Without DEBUG and without a host the answer is a 404 that names the setting
  to configure. A redirect that would point at the request itself (the same host, port and
  path, whatever the scheme: behind a proxy that terminates TLS the request is http) is
  treated as no host; a host on the same domain under another path is still redirected to.
  A malformed port in the Host header matches no address (a redirect, not 500). The loop
  is detected against the Host of the request: a proxy in front of the application must
  preserve the Host header. A symbolic link out of `MEDIA_ROOT` is not served. The OpenAPI
  operations do not change.

## Fixes

- **An invalid id is 404 on every route of an item.** An id that cannot be a primary key
  of the model (`GET /…/not-a-uuid/schema_retrieve/`) failed with 500 (`badly formed
  hexadecimal UUID string`) on the routes that take the id as a string
  (`schema_retrieve`, `schema_update`, `dict_data`, the relationships routes, custom routes
  that call `set_item`/`get_item`), and with 422 on retrieve, update and delete. All of them
  now answer 404 `Item not found`, the response their OpenAPI operations document.
