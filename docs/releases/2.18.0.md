# Bazis 2.18.0

## Fixes

- **A create and an update did not check the `choices` of a field (up to 2.17.0).**
  The request schemas checked only the type, `null` and `blank` of a model field, so a
  `CharField(choices=...)` accepted any string, an `IntegerField(choices=...)` any number,
  and the value was stored, although the OpenAPI schema of the field shows the `enum` of
  its choices. The write now refuses a value that is not one of them: 422 `ERR_VALIDATE`
  with the pointer `/data/attributes/<field>` and the detail "Value 'x' is not a valid
  choice".

  - The accepted values are the `enum` of the schema of the field: the keys of the
    choices, also of `TextChoices`/`IntegerChoices`, of callable choices (called when the
    schema is built) and of grouped choices (the values inside the groups, not the names
    of the groups). The `enum` of grouped choices used to hold the names of the
    groups (and `enumDict` their pairs); it holds the values now.
  - Every element of an array field (`ChoiceArrayField`) must be a choice, an empty or a
    null one too. The column of each language of a translated field is checked as any
    field.
  - `null` and an empty value are left to the checks of `null` and `blank`, as in the
    validation of a Django model field: a `blank=True` field accepts `''` and a
    `null=True` one `null` whether or not they are among the choices.
  - Only the requests are checked: the responses show what the database holds, and
    `save()` in the code does not run the schemas. The fields restricted by bazis-permit
    or bazis-statusy keep the `enum` of the model field.

## Upgrading

- A client that sent a value out of the choices (a language code the project does not
  list, an old status) gets 422 now. The value already stored is still read, but an
  update that sends it back is refused: add it to the choices or migrate the data.
- A field whose choices are narrower than what the project stores (the choices were not
  enforced) should list every accepted value.
