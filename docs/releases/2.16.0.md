# Bazis 2.16.0

## Security

- **An empty list of fields was every field (bazis 2.2.0 to 2.15.1).**
  `SchemaResourceBuilder(factory, fields=[])` built the schema with every field of the
  factory (`fields or factory.fields_list`), so the field permissions of bazis-permit that
  hide every field of a model from a role (`field.view.all.all.__all__.disable` with
  nothing enabled, or under a selector or a status) showed every field instead, in the
  card, the list and `included`. An empty list is now no field; `None` is still every
  field. Upgrade bazis-permit with it (2.11 relies on it); on older versions enable at
  least one field (`__all__.disable` with `<field>.enable`).
- **A disabled field required in the model stayed writable on update (bazis 2.2.0 to
  2.15.1).** `SchemaFactory.fields_patch` hid a field restricted `disable` only when it
  was optional (`not field.required`), outside the schemas of a view. A field required in
  the model (without `blank=True`, `null=True` or a default) therefore stayed in the
  update schema, where no field is required: with bazis-permit,
  `field.change.<selector>.<field>.disable` (or `__all__.disable`) of such a field left
  it writable, an update and the relationships endpoints changed it (200), and so did the
  `included` of an update. Now `disable` hides the field from every schema whatever its
  requiredness, except the create schema: an item cannot be created without a required
  field, so it stays there (bazis-permit warns, `permit.W009`). An update with the field
  is 422, its relationships endpoints answer 403 `ERR_RELATIONSHIP_READONLY`. The transit
  schema of bazis-statusy no longer validates such a field either. A field whose own
  restrictions say `required` (`<field>.required` with `__all__.disable`) stays in the
  schema as before, in the transit schema validated; `__all__.required` does not keep a
  field its own restriction disables. On older versions,
  declare the field `readonly` on change instead of `disable`
  (`field.change.<selector>.<field>.readonly`: an update ignores it).

## Breaking changes

- **A unique or an exclusion constraint answers 409 `ERR_CONFLICT`.** An `IntegrityError`
  of a unique or an exclusion constraint anywhere in a request (also two parallel creates
  of the same value, or a violation at the commit) is 409 with the code `ERR_CONFLICT`
  and the detail "The change conflicts with the current data" (`meta.constraint` names
  the constraint with DEBUG). On the create and the update of a route, a unique
  constraint of its model (a `UniqueConstraint` of `Meta.constraints`, also of expressions
  such as `Lower('email')`, a `unique=True` field, a `unique_together`) whose fields the
  user all writes (in the schema of the write he has, not read-only) answers an error for
  each of its fields, at `/data/relationships/<f>` or `/data/attributes/<f>`, with the
  message of Django ("Reader with this Memo and E-mail already exists.", or the
  `violation_error_message` of the constraint): a form shows a parallel duplicate at its
  field, as the 422 of a sequential one. Any other keeps the single error without a
  pointer and without a name of a field: a field hidden from the user or filled by the
  server (an author, a number), a constraint of another table (a child an action
  creates), an action, the relationships endpoints, an exclusion constraint. A create answered 409 `ERR_REQUEST` "Data conflict" for any integrity error before: a
  not-null or a check violation of a create is now a 500, like on the other routes (keep
  such rules in `validate_item`, 422).
- **A request aborted for a parallel one answers 409 `ERR_CONFLICT` with `meta.retry`.**
  A deadlock (SQLSTATE 40P01) or a serialization failure (40001) was a 500; it is 409
  `ERR_CONFLICT` "The request conflicted with a parallel one: retry it" with
  `meta: {"retry": true}` (`meta.sqlstate` with DEBUG). The transaction of the request is
  rolled back; the core does not repeat it, the client may send it again. A client that
  read every 409 as a unique conflict tells the two apart by `meta.retry`. Any other
  `OperationalError` stays a 500.
- **A Django `ValidationError` outside `validate_item` answers 422.** Raised in a hook, a
  route or a lookup by a value that cannot be a key (`filter(pk='not-a-uuid')` in an
  action that types the id as `str`), it was a 500; it is 422 `ERR_ITEM_INVALID` like an
  error of `validate_item`, without an item (a field of a dict at
  `/data/relationships/<field>` for a relation of the model of the route, else at
  `/data/attributes/<field>`, a message without a field at `/data`; on GET a field at
  `/query/<field>`, a message without a field with no pointer), and a WARNING of the logger `bazis.core.app_factory` names the
  route with the traceback. The rules still belong in `validate_item`, and the guide types
  the ids of the bodies and the queries of the actions as keys (`UUID`), which the request
  schema checks first (422 `ERR_VALIDATE`). `JsonApiItemInvalidException` takes
  `item=None` and `model`.
- **A `URLField` accepts only a URL or an empty string.** Its type was
  `AnyUrl | constr(max_length=0) | None`, where the `constr` inside `Annotated` was
  ignored: any string passed (`javascript:alert(1)`), and with `max_length` the JSON schema
  was a nested `anyOf` without a `type`. The type (`bazis.core.utils.django_types.url_type`,
  `url_field_type(model_field)`) now takes the schemes of the `URLValidator`s of the field
  (http, https, ftp, ftps by default) and its `max_length` (also of the normalized URL);
  anything else is 422 `ERR_VALIDATE` with one error at the attribute. The value is stored
  normalized (`https://example.com` → `https://example.com/`). The JSON schema is a flat
  `anyOf: [{type: string, format: uri, minLength: 1, maxLength}, {type: string,
  maxLength: 0}]` (+ `{type: null}` for a nullable field), in the requests and the
  responses. A response shows the stored value as it is, so a value written before is
  still read (and refused when written again: fix such rows by a data migration).
  `validators=` with no scheme in common with the default `URLValidator` is
  `ImproperlyConfigured` naming the field; other schemes need a subclass of `URLField`
  with its own `default_validators`.
- **`x-bazis` always has `public`** (`true` for an action declared `public=True`, else
  `false`); `access_action` is there when the route declares it, `/_id/` declares
  `view` (with bazis-permit 2.11 it is open as `GET /`, also to the roles for anonymous
  users).
- **`set_item` returns the item the route holds only for the same id**, and
  `set_item(item_id, with_lock=True)` takes it again, locked, when it was not taken locked
  (bazis-permit 2.11 takes the item of an action with `access_action` before the action
  runs, locked for the methods that write). It returned the held item for any id before.
- **`migrate` installs the triggers of the models.** The triggers of pgtrigger (the
  `dt_created`/`dt_updated` of the core, the current role of bazis-permit, the
  `Meta.triggers` of a project) are not in the migrations, and only `manage.py pgtrigger
  install` installed them: the databases of the projects that ran only `migrate` lacked
  them, while the test databases (bazis-test-utils) had them. `migrate` now installs the
  missing and outdated ones once all the migrations of the database are applied, each in
  a short transaction under the lock of the declarations that waits for the lock of its
  table at most `BAZIS_TRIGGERS_LOCK_TIMEOUT` seconds (5; past it `migrate` fails, naming
  the trigger, and is run again). A `migrate` with nothing to change runs no DDL; a
  `migrate` to an earlier migration and `flush` install nothing. The first `migrate` after
  the upgrade installs them in a database that lacks them: the rules they keep start to
  apply to its writes (the existing rows are not changed). `migrate` removes no trigger:
  the triggers of pgtrigger that no model declares (stale, or of another project in the
  same database) are kept and reported. `PGTRIGGER_INSTALL_ON_MIGRATE` stays off: the
  receiver of pgtrigger installs all the triggers (and prunes the others) after every
  `migrate`, also a partial one, and after every `flush`. The installed triggers fire
  during the later migrations: run a migration that removes or renames a column a trigger
  reads, or a data migration that must not fire them, after `manage.py pgtrigger
  uninstall <uri>` of those triggers (without a URI the command also removes the triggers
  of pgtrigger of another project that shares the database). Run `migrate` as a deploy
  step of its own before the new version starts: a `migrate` of the old version after it
  installs the old triggers again. The deploy script of the sample no longer uninstalls
  and installs all the triggers around `migrate`. `bazis_doctor` warns of the missing or
  outdated triggers and of the ones no model declares (`bazis.W008`, a database check).
- **A dynamic setting follows its `BS_*` variable until a value is set.** constance saved
  the default of a setting (its `BS_*` variable) on its first read, also by the admin page
  and `manage.py constance get`, so a variable set later had no effect (an empty
  `DEFAULT_FROM_EMAIL` read once made every mail fail with `Invalid address ''`, whatever
  `BS_DEFAULT_FROM_EMAIL` said later). The default `CONSTANCE_BACKEND` is now
  `bazis.core.constance_conf.backend.DatabaseBackend`, which does not save the default of
  a setting without a saved value: a value is saved only when it is set (the admin,
  `manage.py constance set`, `config.X = ...`) and then wins over the variable. The values
  saved before stay saved (the guide shows how to delete them); a value equal to the
  default is not saved. With `CONSTANCE_DATABASE_CACHE_BACKEND` the absence of a value is
  cached too. A project that sets `CONSTANCE_BACKEND` keeps its backend. Requires
  django-constance 4.3.5.
- **`DEFAULT_FROM_EMAIL` defaults to `webmaster@localhost`** (the default of Django), not
  an empty string, with which every mail failed. `bazis_doctor` warns of an empty sender
  (`bazis.W009`, a database check: the value saved in the database) and names the fix
  (`manage.py constance set DEFAULT_FROM_EMAIL noreply@<domain>`).
- **The forward side of a many-to-many relation with a `through` model of the project is
  written, and honors `blank`.** It was required in the create schema whatever its
  `blank` (`blank=True` was ignored), and made optional (`SchemaField(required=False)`) it
  became read-only: the relation sent in the document was dropped silently. It is now
  written like any many-to-many relation (`set()`), optional with `blank=True` or a
  default; its reverse side stays read-only. `set()` writes the rows of the through model
  without `save()`: a through model whose other required columns have no default (and are
  not filled by the database) now fails such a write with an `IntegrityError` (a 500)
  where the relation was dropped before; give them defaults, or keep the relation out of
  the schema. The guide has the recipe "no overlapping intervals of a participant": the
  through model holds the interval of its parent, filled by triggers, under an exclusion
  constraint (`btree_gist`).

## Upgrade

- **The triggers.** The first `migrate` installs the triggers of pgtrigger in a database
  that never had them (a production database migrated only with `migrate`): from then on
  `set_dt_created`/`set_dt_update` of the core set `dt_created` and `dt_updated` to the
  time of the statement on every insert and update (a value written by the code or an
  import is replaced), and the triggers of bazis-permit keep `role_current` of a user one
  of his roles: they do not refuse a write, they change it. A save of a user whose
  current role is empty or not one of his roles sets it to his first role (empty without
  roles); adding a role to a user without a current role sets it, removing his current
  role sets the first remaining one. The existing rows are not changed until written.
- Run `migrate` as a deployment step of its own, before the processes of the new version
  start; never run the `migrate` of an older version after a newer one (it installs its
  own triggers again over the newer ones).
- A trigger waits for the lock of its table at most `BAZIS_TRIGGERS_LOCK_TIMEOUT` (5 s):
  past it `migrate` fails after its migrations are applied, naming the trigger; run it
  again.
- Before the release, on a copy of the production database: run `migrate` twice (the
  second one installs nothing: no DDL, no "Installed ... trigger(s)" line); run
  `bazis_doctor` (no `bazis.W008`, no `bazis.W009`); count the users whose `role_current`
  is empty while they have roles, or is not one of their roles (the triggers of
  bazis-permit change it on their next save);
  measure the time of `migrate` under the usual background writes.
- **The dynamic settings.** A database used before 2.16 has saved the defaults of the
  dynamic settings at their first read (`manage.py constance list`, the table
  `constance_constance`): they keep winning over the `BS_*` variables. Compare them with
  the variables, and delete the saved values that should follow their variable (the
  guide, Settings: `BS_*`); `bazis_doctor` warns of an empty `DEFAULT_FROM_EMAIL`
  (`bazis.W009`).

## Changes

- **A list never fails for an object of an unknown schema key.** `JsonApiTopListSchema`
  shows an object whose `_schema_key` (the combination of its field groups, bazis-permit)
  has no member of the schema with the member without a key, the fields shown in every
  object, and logs a warning; it raised a `KeyError` (a 500 of the whole list).
- **`lock_on_write`: the parent locked before every write of an item.** A model names
  foreign keys in the class attribute `JsonApiMixin.lock_on_write` (`('memo',)`): every
  save of an item, whatever writes it (the routes, the actions, the admin, scripts, the
  transits of bazis-statusy), locks the rows they point to (`SELECT ... FOR NO KEY UPDATE`,
  by the current values; an empty key is skipped) before it writes, until the commit.
  `validate_item` then counts under that lock, and a create takes the locks in the order
  of an action that locks the parent first and then creates the item: the two no longer
  deadlock (a parent locked only in `validate_item`, after the insert, deadlocked with
  such an action on a unique value). A model without `validate_item` may declare it too;
  the items of such a model that a reverse foreign key links (the relationships
  endpoints, the create and the update of the parent with the relation) are saved one by
  one, with the lock, instead of one bulk update. `set_item(item_id, with_lock=True)` on
  the route of such a model locks the parents before the item, so the actions of an item
  (also those bazis-permit checks with `access_action`, the transits of bazis-statusy)
  take the locks in the order of the writes of the parent. `QuerySet.update()`,
  `bulk_create()`, `bulk_update()`, raw SQL, the many-to-many managers and the deletion
  stay outside.
- **Relationships: the objects a user may link.** `relations_access_check` asks
  `restrict_queryset` of the default route of the related model for the objects a
  relationship links with `link=True` (not for the objects a reverse relationship unlinks:
  they are checked for `change` without it). An override may return fewer objects then:
  the ones the user may link, though they see more (bazis-uploadable 2.7 links only the
  own files of a user). A visible object the override leaves out fails with 422
  `ERR_RELATION_LINK` with the pointers of `ERR_RELATION_ACCESS`; an invisible one stays
  403 `ERR_RELATION_ACCESS`. A successful check needs one query (two when a reverse
  relationship both links and unlinks). An override of `restrict_queryset` must accept
  `**kwargs` (as documented).
- **Who may call an action.** The `http_*` decorators take `public` (an action open to
  anonymous users) and `access_action` (the permission it requires): the route context
  keeps them, an override keeps them unless it declares its own (as `kind`), and the
  `x-bazis` extension of the OpenAPI operation shows them. The core records them (without
  bazis-permit `public` only adds the default throttle); bazis-permit 2.11 enforces them
  in the new hook `InitialRouteBase.route_check`, which runs before the function of a
  route, in its transaction. `route_declare(route, **facts)` declares an inherited route
  again with another `kind`, `public`, `access_action` or `dependencies`
  (`action_transit = route_declare(StatusyRouteSetBase.action_transit, public=True)`).
- **Request rate limits.** `bazis.core.throttle.throttle(rate, key='user_or_ip',
  scope=None)` is a FastAPI dependency (`dependencies=[throttle('10/minute')]`): a fixed
  window in the default cache (Redis), 429 `ERR_THROTTLED` with `Retry-After` over the
  rate. It counts the user of the route (`self.inject.user`) or the IP address of an
  anonymous one (`key='ip'`: always the address); `scope` shares a count among routes; the
  rate may be a callable read per request (a dynamic setting; an invalid one is logged and
  does not limit). The actions declared `public=True` get `BAZIS_THROTTLE_PUBLIC`
  (`'30/minute'` per user or IP address, dynamic, validated in the environment and the
  admin, `''` turns it off) unless they declare their own throttle. The default applies at
  once to every existing `public=True` action: an action called more than 30 times a minute
  by one user or IP address now answers 429 without any change of code. Set
  `BAZIS_THROTTLE_PUBLIC=''` to leave the public actions unlimited.
  `BAZIS_THROTTLE_ENABLED` (dynamic) turns all the limits off, `BAZIS_THROTTLE_EXEMPT` (an
  import path of a function `(request, ident) -> bool`) exempts requests, for example by a
  whitelist of the project or in load tests and CI. With a local-memory cache (LocMem) the
  count is per process, so the effective limit is multiplied by the number of workers; use
  Redis for a shared count. The limits fail open: when the cache is unavailable they are not
  applied and a WARNING "Throttle of <scope> not applied: the cache failed" is logged. The
  address is the one uvicorn gives: the deploy template of the samples trusts
  `X-Forwarded-For` only from `BS_FORWARDED_ALLOW_IPS` (default loopback and the private
  networks) instead of `'*'`; a CIDR in this list needs uvicorn>=0.30.
  `throttle_reset()` forgets all the counts (the keys `bazis:throttle:*` of the default
  cache): the pytest plugin of bazis-test-utils 2.5.2 calls it before each test.
- **The SMTP connection has a timeout.** `DynamicSMTPEmailBackend` opened the connection
  without one: an unresponsive mail server held the request (or the task) that sent a
  mail, e.g. bazis-notify sending after the commit of a request. The dynamic setting
  `BAZIS_EMAIL_TIMEOUT` (seconds, default 10, `BS_BAZIS_EMAIL_TIMEOUT` as its initial
  value) bounds the connection and every command to the server; a timeout fails the
  sending with an `OSError` (`TimeoutError`, or `smtplib.SMTPServerDisconnected` once
  connected). 0 restores the wait without a limit; `timeout` in the `OPTIONS` of
  `MAILERS['default']` overrides it. The guide advises catching `OSError` (it covers
  `smtplib.SMTPException` and the connection errors) when sending.
- **`dependencies=` of the `http_*` decorators works.** The registration copied the route
  parameters with `dataclasses.asdict`, which turned the `Depends` of `dependencies` into
  dicts. The registration no longer writes into the declared parameters of a route: a
  subclass made after its base was registered got the name of the route of the base.
- **`bazis.core.declare`: the helpers of the declarations in the code** that `migrate`
  applies (the roles of bazis-permit, the workflows of bazis-statusy, the schedules of
  bazis-bg), moved from bazis-permit: `discover` (the declarations of the `<app>.<module>`
  modules), `lock` (the advisory lock that serializes concurrent `migrate` runs),
  `migrations_complete`, `apply_after_migrate` (the work of a `post_migrate` receiver),
  `ManagedSync` and `managed_orphans` (the objects of a model with a unique `slug` and a
  `managed` flag: created, updated or taken over with a warning) and
  `bazis.core.admin_abstract.ManagedAdminMixin` (the declared objects read-only in the
  admin).
- **The internal columns of a model stay out of the schemas.** The classmethod
  `InitialBase.get_fields_hidden()` (an empty set, extended with `super()`) names the
  fields that the default schemas of the routes leave out: a route has one only when it
  names it in `include` or `origin`. bazis-permit 2.11 hides its generated selector arrays
  (`autogen_<field>_selectors`) with it.
- The guide documents the invariants under concurrent requests ("no more than N per
  parent": the parent declared in `lock_on_write`, the count in `validate_item`, the
  number taken under the lock in `save()`, a `UniqueConstraint` as the barrier,
  `set_item(with_lock=True)` in an action, one order of the locks, a test of parallel
  requests with `parallel` of bazis-test-utils 2.5.2), the rate
  limits and the e-mail of the core (`BAZIS_EMAIL_*`, `DynamicSMTPEmailBackend`), and a
  calculated field with nothing to fetch (`@calc_property([])` or a `@property`).
- The guide says that a required text of the body of an action strips the whitespace
  before its length is checked (`StringConstraints(strip_whitespace=True, min_length=1)`):
  `Field(min_length=1)` accepts a text of only spaces.
- The examples of `calc_property` in the guide compute the value in the method for the
  reads outside the query of a route: they returned the attribute itself
  (`return self.open_tickets`), which calls the method again on an item read without the
  annotation (the admin, the shell, the children of a transit of bazis-statusy < 2.12):
  a `RecursionError`.
- The `test` extra requires bazis-test-utils 2.5.2: the tests use its `parallel()`
  (bazis-test-utils does not depend on Bazis, so it is released first).
- The guide is read by sections: its introduction maps them with when to read each, the
  long sections are split by topic ("Invariants of the items", "Calculated fields",
  "Custom routes and actions", "Writes and errors"), and the items of the manifest are one
  line each, their details in the guide (the default read of the guide with its manifest
  went from 29 to 17 kB). The guide adds that a forward relation is required in the
  create schema unless its field is `blank`, `null` or has a default, and how `search`
  matches several words (each word in one of the search fields; a field through a
  relation matches the whole value).
