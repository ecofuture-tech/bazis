# Bazis 2.16.0

## Breaking changes

- **A unique or an exclusion constraint answers 409 `ERR_CONFLICT`.** An `IntegrityError`
  of a unique or an exclusion constraint anywhere in a request (also two parallel creates
  of the same value, or a violation at the commit) is 409 with the code `ERR_CONFLICT`
  and the detail "The change conflicts with the current data" (`meta.constraint` names
  the constraint with DEBUG). A create answered 409 `ERR_REQUEST` "Data conflict" for any integrity error before: a
  not-null or a check violation of a create is now a 500, like on the other routes (keep
  such rules in `validate_item`, 422).
- **A request aborted for a parallel one answers 409 `ERR_CONFLICT` with `meta.retry`.**
  A deadlock (SQLSTATE 40P01) or a serialization failure (40001) was a 500; it is 409
  `ERR_CONFLICT` "The request conflicted with a parallel one: retry it" with
  `meta: {"retry": true}` (`meta.sqlstate` with DEBUG). The transaction of the request is
  rolled back; the core does not repeat it, the client may send it again. A client that
  read every 409 as a unique conflict tells the two apart by `meta.retry`. Any other
  `OperationalError` stays a 500.
- **A Django `ValidationError` outside `validate_item` answers 422.** Raised in a hook, a
  route or a lookup by a value that cannot be a key (`filter(pk='not-a-uuid')` in an
  action that types the id as `str`), it was a 500; it is 422 `ERR_ITEM_INVALID` like an
  error of `validate_item`, without an item (the pointer `/data/attributes/<field>` for a
  dict, `/data` otherwise), and a WARNING of the logger `bazis.core.app_factory` names the
  route with the traceback. The rules still belong in `validate_item`, and the guide types
  the ids of the bodies and the queries of the actions as keys (`UUID`), which the request
  schema checks first (422 `ERR_VALIDATE`). `JsonApiItemInvalidException` takes
  `item=None`.
- **`x-bazis` always has `public`** (`true` for an action declared `public=True`, else
  `false`); `access_action` is there when the route declares it, `/_id/` declares
  `view` (with bazis-permit 2.11 it is open as `GET /`, also to the roles for anonymous
  users).
- **`set_item` returns the item the route holds only for the same id**, and
  `set_item(item_id, with_lock=True)` takes it again, locked, when it was not taken locked
  (bazis-permit 2.11 takes the item of an action with `access_action` before the action
  runs, locked for the methods that write). It returned the held item for any id before.

## Changes

- **`lock_on_write`: the parent locked before every write of an item.** A model names
  foreign keys in the class attribute `JsonApiMixin.lock_on_write` (`('memo',)`): every
  save of an item, whatever writes it (the routes, the actions, the admin, scripts, the
  transits of bazis-statusy), locks the rows they point to (`SELECT ... FOR NO KEY UPDATE`,
  by the current values; an empty key is skipped) before it writes, until the commit.
  `validate_item` then counts under that lock, and a create takes the locks in the order
  of an action that locks the parent first and then creates the item: the two no longer
  deadlock (a parent locked only in `validate_item`, after the insert, deadlocked with
  such an action on a unique value). A model without `validate_item` may declare it too.
  `QuerySet.update()`, `bulk_create()` and `bulk_update()` stay outside, as with
  `validate_item`.
- **Relationships: the objects a user may link.** `relations_access_check` asks
  `restrict_queryset` of the default route of the related model for the objects a
  relationship links with `link=True` (not for the objects a reverse relationship unlinks:
  they are checked for `change` without it). An override may return fewer objects then:
  the ones the user may link, though they see more (bazis-uploadable 2.7 links only the
  own files of a user). A visible object the override leaves out fails with 422
  `ERR_RELATION_LINK` with the pointers of `ERR_RELATION_ACCESS`; an invisible one stays
  403 `ERR_RELATION_ACCESS`. A successful check needs one query (two when a reverse
  relationship both links and unlinks). An override of `restrict_queryset` must accept
  `**kwargs` (as documented).
- **Who may call an action.** The `http_*` decorators take `public` (an action open to
  anonymous users) and `access_action` (the permission it requires): the route context
  keeps them, an override keeps them unless it declares its own (as `kind`), and the
  `x-bazis` extension of the OpenAPI operation shows them. The core records them (without
  bazis-permit `public` only adds the default throttle); bazis-permit 2.11 enforces them
  in the new hook `InitialRouteBase.route_check`, which runs before the function of a
  route, in its transaction. `route_declare(route, **facts)` declares an inherited route
  again with another `kind`, `public`, `access_action` or `dependencies`
  (`action_transit = route_declare(StatusyRouteSetBase.action_transit, public=True)`).
- **Request rate limits.** `bazis.core.throttle.throttle(rate, key='user_or_ip',
  scope=None)` is a FastAPI dependency (`dependencies=[throttle('10/minute')]`): a fixed
  window in the default cache (Redis), 429 `ERR_THROTTLED` with `Retry-After` over the
  rate. It counts the user of the route (`self.inject.user`) or the IP address of an
  anonymous one (`key='ip'`: always the address); `scope` shares a count among routes; the
  rate may be a callable read per request (a dynamic setting; an invalid one is logged and
  does not limit). The actions declared `public=True` get `BAZIS_THROTTLE_PUBLIC`
  (`'30/minute'` per user or IP address, dynamic, validated in the environment and the
  admin, `''` turns it off) unless they declare their own throttle. The default applies at
  once to every existing `public=True` action: an action called more than 30 times a minute
  by one user or IP address now answers 429 without any change of code. Set
  `BAZIS_THROTTLE_PUBLIC=''` to leave the public actions unlimited.
  `BAZIS_THROTTLE_ENABLED` (dynamic) turns all the limits off, `BAZIS_THROTTLE_EXEMPT` (an
  import path of a function `(request, ident) -> bool`) exempts requests, for example by a
  whitelist of the project or in load tests and CI. With a local-memory cache (LocMem) the
  count is per process, so the effective limit is multiplied by the number of workers; use
  Redis for a shared count. The limits fail open: when the cache is unavailable they are not
  applied and a WARNING "Throttle of <scope> not applied: the cache failed" is logged. The
  address is the one uvicorn gives: the deploy template of the samples trusts
  `X-Forwarded-For` only from `BS_FORWARDED_ALLOW_IPS` (default loopback and the private
  networks) instead of `'*'`; a CIDR in this list needs uvicorn>=0.30.
  `throttle_reset()` forgets all the counts (the keys `bazis:throttle:*` of the default
  cache): the pytest plugin of bazis-test-utils 2.5.2 calls it before each test.
- **The SMTP connection has a timeout.** `DynamicSMTPEmailBackend` opened the connection
  without one: an unresponsive mail server held the request (or the task) that sent a
  mail, e.g. bazis-notify sending after the commit of a request. The dynamic setting
  `BAZIS_EMAIL_TIMEOUT` (seconds, default 10, `BS_BAZIS_EMAIL_TIMEOUT` as its initial
  value) bounds the connection and every command to the server; a timeout fails the
  sending with an `OSError` (`TimeoutError`, or `smtplib.SMTPServerDisconnected` once
  connected). 0 restores the wait without a limit; `timeout` in the `OPTIONS` of
  `MAILERS['default']` overrides it. The guide advises catching `OSError` (it covers
  `smtplib.SMTPException` and the connection errors) when sending.
- **`dependencies=` of the `http_*` decorators works.** The registration copied the route
  parameters with `dataclasses.asdict`, which turned the `Depends` of `dependencies` into
  dicts. The registration no longer writes into the declared parameters of a route: a
  subclass made after its base was registered got the name of the route of the base.
- **`bazis.core.declare`: the helpers of the declarations in the code** that `migrate`
  applies (the roles of bazis-permit, the workflows of bazis-statusy, the schedules of
  bazis-bg), moved from bazis-permit: `discover` (the declarations of the `<app>.<module>`
  modules), `lock` (the advisory lock that serializes concurrent `migrate` runs),
  `migrations_complete`, `apply_after_migrate` (the work of a `post_migrate` receiver),
  `ManagedSync` and `managed_orphans` (the objects of a model with a unique `slug` and a
  `managed` flag: created, updated or taken over with a warning) and
  `bazis.core.admin_abstract.ManagedAdminMixin` (the declared objects read-only in the
  admin).
- **The internal columns of a model stay out of the schemas.** The classmethod
  `InitialBase.get_fields_hidden()` (an empty set, extended with `super()`) names the
  fields that the default schemas of the routes leave out: a route has one only when it
  names it in `include` or `origin`. bazis-permit 2.11 hides its generated selector arrays
  (`autogen_<field>_selectors`) with it.
- The guide documents the invariants under concurrent requests ("no more than N per
  parent": the parent declared in `lock_on_write`, the count in `validate_item`, the
  number taken under the lock in `save()`, a `UniqueConstraint` as the barrier,
  `set_item(with_lock=True)` in an action, one order of the locks, a test of parallel
  requests with `parallel` of bazis-test-utils 2.5.2), the rate
  limits and the e-mail of the core (`BAZIS_EMAIL_*`, `DynamicSMTPEmailBackend`), and a
  calculated field with nothing to fetch (`@calc_property([])` or a `@property`).
- The `test` extra requires bazis-test-utils 2.5.2: the tests use its `parallel()`
  (bazis-test-utils does not depend on Bazis, so it is released first).
