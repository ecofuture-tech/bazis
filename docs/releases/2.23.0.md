# Bazis 2.23.0

## Changed

- **The search reaches the fields the route shows the user, in the list or on the card.**
  `search`, `$search` of `filter`, `<relation>__$search` and a search field through a
  relation (`tag__name`) searched only the fields of the LIST schema of the route, so a
  field that the list leaves out to stay light (a long text) but the card shows could not
  be searched without adding it to every object of the list. They now reach the fields of
  the LIST or the RETRIEVE schema of the route for the user (`QueryScope.read_fields`);
  through a relation, those of the default route of the related model, in the objects it
  shows (its `restrict_queryset`, as before). A route that does not declare
  `search_fields` searches the text fields of both: those of the LIST schema in its order,
  then those only the RETRIEVE schema has. The set only grows: every field a route
  searched in 2.22 is still searched.

  What stays:

  - `filter`, `sort` and `aggregate` reach only the LIST schema. A field only the card
    shows is searched, but a key of `filter` or `sort` by it is 400 `ERR_FILTER`, the
    answer for a field that does not exist; `<relation>__$search` as a key of `filter`
    needs the relation in the LIST schema.
  - A field the route hides in both schemas (a `None` key of `fields`, or a projection of
    LIST and RETRIEVE), or that a package hides per user, is not searched, and the answer
    does not tell it from a field that does not exist.
  - A route that does not serve RETRIEVE (no `action_retrieve` in its `actions`, or in
    `actions_exclude`) searches its LIST schema only, as before. The RETRIEVE schema that
    the responses of its create or update use does not count: they show the objects the
    user writes, not every object of the list.
  - The LIST schema, its OpenAPI, `schema_list`, `included` and `query_fields()` without
    `api_action` are as they were.

  `route_search_fields(route_cls)` and the check `bazis.W007` use the same fields (of a
  registered route), so a declared search field that only the card shows is no longer
  reported. The text of W007 is now: "The search field '...' of the route set is not a
  field the route shows (its LIST or RETRIEVE schema; through a relation, of the default
  route of the related model): the search leaves it out."

## API

- `JsonapiRouteBase.query_fields(user=None, *, api_action=CrudApiAction.LIST, **kwargs)`:
  the fields of the schema of a read action (`LIST` or `RETRIEVE`) for the user; for
  `RETRIEVE` of a route that does not serve it, those of LIST. `api_action` is
  keyword-only.
- `JsonapiRouteBase.query_schema_factory(api_action=CrudApiAction.LIST)`: the schema factory
  that `query_fields` reads, for a package that builds the fields per user from it
  (bazis-permit). It replaces the factory of a route without the list action that
  `query_fields` built inside (`_query_schema_factory`).
- `QueryScope(..., read_fields=...)` and `QueryScope.allows(name, model, read=True)`: the
  fields of the search; `fields` and `order_fields` (the filter and the sorting) are
  unchanged.

## Upgrading

Nothing is required in a project that does not override `query_fields`. The search of a
route without `search_fields` may now include text fields its card shows (`TextField`s
too): on a large list declare `search_fields` (or `[]`), as the rule of 2.20 says. The
contract of bazis-front lists the search fields of a resource: generate it again
(`bazis-front update`), the `search` of a resource without `search_fields` may grow.

A package or a project that overrides `query_fields`:

- An override with `**kwargs` keeps working: it gets `api_action` in `**kwargs`. One that
  passes them on to `super()` (bazis-bg) gives the fields of both schemas. One that does
  not (bazis-permit up to 2.11) gives its LIST fields for `RETRIEVE` too: the search stays
  within the LIST schema, as in 2.22. With bazis-permit before 2.12 nothing is exposed, the
  new search of the cards is simply not there for its routes; bazis-permit 2.12 applies the
  field permissions to the RETRIEVE schema the same way as to LIST.
- An override without `**kwargs` (`def query_fields(cls, user=None)`) now fails with a
  `TypeError` on every request of the route: add `*, api_action=CrudApiAction.LIST,
  **kwargs` and return the fields of the schema of `api_action`, from
  `cls.query_schema_factory(api_action)` or `super().query_fields(user, api_action=...)`.
  Narrow both actions the same way: a field the override leaves out of LIST only, while
  the core RETRIEVE schema shows it, is searched.

The search assumes that the card of a route shows every object of its list (the core and
bazis-permit restrict both with one `restrict_queryset` for `view`). A route whose own
`get_queryset_for_item` shows fewer objects than its list shows on the card only the
fields that may be searched in every object of the list.
