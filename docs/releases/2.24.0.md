# Bazis 2.24.0

## Security

- **The type and the id of a request document are checked against the route.** The
  `type` of the `data` of a create or an update document was not compared with the route
  (every release up to 2.23.0). On a create the core took the model to create from it
  (`JsonApiDataSchema.build_for`): a POST to the route of one model with the `type` of
  another model whose fields have the names of the attributes of the route built and saved
  an object of that other model, also a child model of the model of the route or a model
  without a route of its own, through the route, its hooks and its checks of the first
  model (`hook_before_create`, `validate_item` and `hook_after_create` ran on that object).
  The object stayed in the database when the response found an object of the route with
  the same id (integer keys), else the request answered 404 and was rolled back; an
  unknown, an empty or an unfitting `type` answered 500. On an update the `type` was
  ignored, and so was a `data.id` that is not the id of the path (the object of the path
  was changed). Now a `type` that is not the type of the route (on an update, nor the type
  the route shows the item with) or an `id` of an update that is not the id of the path is 409
  `ERR_RESOURCE_MISMATCH` with the pointer `/data/type` or `/data/id` (both errors in one
  response when both differ), as JSON:API requires, and nothing is written, no hook runs.
  The model of a write is the model of the schema of the route, never the text of the
  request (`build_for` and `relations_access_check` take `schema_factory.model`). A
  document without `type` is written as before, on a create and on an update;
  the `id` of an update stays required (422 `ERR_VALIDATE` at `/data/id`) and is compared
  as a key of the model (a UUID in any case); the `id` of a create is still the id of the
  client. `included` is unchanged: its items are validated by the schema of their type.
  Before 2.24.0 an object of another model could remain in the database when integer
  ids of the two models coincided; if the routes were reachable by untrusted clients,
  check the data and the logs of the hooks.

## Changed

- The OpenAPI of the create and the update routes lists 409 (`SchemaErrors`): the new
  error and the 409 `ERR_CONFLICT` of a unique constraint, which they already answered.
- `JsonapiRouteBase.item_create` no longer answers 400 "Data type is invalid": the branch
  could not be reached (an unknown type was a 500), and the message is gone from the
  catalogs.

## Upgrading

A client that sends an inexact `type` (a document copied from another resource, the type
of a child model on the route of its parent, a label in another case such as
`catalog.Attachment`) or, in a PATCH, the `id` of another object now gets 409: send the
`type` the route answers (the `data.type` of its responses, the `type` of the resource in
the contract of bazis-front) or leave it out, and the `id` of the path. bazis-front, and
the packages that write through the routes (bazis-uploadable, bazis-bulk, which replays
each operation through the application), send both from the route; nothing changes there.
There is no setting to turn the check off: it closes the creation of objects of other
models through a route.
The check lives in `JsonapiRouteBase.create()` and `update()`: a route of a product that
overrides them without calling `super()` does not get it.

A route whose queryset gives the instances of a child model shows them under the type of
that model: a PATCH takes that type, the type of the route or none (another type is 409);
a POST takes only the type of the route, or none.
