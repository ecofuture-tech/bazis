# Bazis 2.9.0

The filter, the sorting and the search of a request reach only what the route shows the
user. Breaking: a key out of the LIST schema of the route, a relation into objects the
user cannot see, and `search` on a route without `search_fields` no longer work; the
transitional setting `BS_BAZIS_FILTERS_STRICT=false` restores the behavior of 2.8.

## Security

- **The filter, the sorting and the search could read the data a route hides.** They
  accepted any field of the model and any relation: on a route that shows only some
  fields of its model (a projection with `fields`), `filter=title=...`,
  `filter=author__username=...`, `sort=title` and `search=...` (a route without
  `search_fields` searched every text and integer field of the model) let a client find
  out the values of the hidden fields by trial; and a filter through a relation
  (`filter=bookings__title=...` on another resource, also a reverse relation) reached the
  related objects the user cannot see. Now (`BAZIS_FILTERS_STRICT`, on by default):
  - a key of `filter` starts with a field of the LIST schema of the route that can
    filter (its `filterLabel`) or `id` (`pk`), a term of `sort` with a field that can order (its
    `orderLabel`);
  - a relation of the schema leads into the related objects the default route of the
    related model shows (its `restrict_queryset` for `view`, with the user of the route, as
    the relationships and `included` since 2.7), and the key goes on with the fields of the
    LIST schema of that route; a related model without a route gives only `id` (`pk`),
    `__exists` and `__isnull`. `sort` follows to-one relations only: the related object
    the user cannot see sorts as null, and a to-many relation does not sort;
  - `search` and `$search` search only the `search_fields` of the route (of the default
    route of the related model for `rel__$search`) that are fields of its LIST schema, a
    relation in a search field into the visible objects; a route without search fields has
    no search;
  - `filter=<app>.<model>=<ids>` (the objects related to those objects) goes only through
    the relations of the schema of the route and only to the given objects the user can
    see.

  Anything else is 400 `ERR_FILTER` with the pointer `/query/filter`, `/query/sort` or
  `/query/search`, the same answer as for a field that does not exist, so that the answer
  does not tell that a hidden field exists. The restriction is applied by the services of
  the list (`ServiceFiltering`, `ServiceSearching`, `SortingSearching`) with the scope of
  the route of the request (`JsonapiRouteBase.query_scope()`, `QueryScope`), also when a
  route calls them itself.

## Changes

- **`JsonapiRouteBase.query_fields(user=None, **kwargs)`** (classmethod): the fields of the
  LIST schema of the route for the user, the roots of the keys. A package that changes the
  LIST schema per user overrides it (bazis-permit, see Upgrading).
- **`QueryToOrm`, `SearchToOrm` and `QueryToOrm.qs_apply` take `scope`** (`QueryScope`);
  without it (the default) they are not restricted, as before: the conditions written in
  the code (the permissions of bazis-permit, the `filter:` restrictions of the fields) use
  any field. The services take `scope` too; by default it is the scope of the route of the
  request, `scope=None` is not restricted. `filters_aliases` of a route are its own filters:
  the names an alias gives are not checked, the relations they lead to are.
- **`SearchToOrm` with a scope** raises `ValueError` for a search without a search field
  in the scope; without a scope it still searches every text field of the model when no
  search fields are given (the deprecated `Searching` too).
- **An invalid `sort` is 400 `ERR_FILTER`** with the pointer `/query/sort` (it was 422
  `ERR_VALIDATE` at `/path/sort`), and a sort by a to-many relation is invalid.
- `bazis_doctor`: `bazis.W006`, `BAZIS_FILTERS_STRICT` is off; `bazis.W007`, a search field
  of a route is not a field of its LIST schema (the search leaves it out).

## Upgrading

- A client that filters, sorts or searches by a field the route does not show gets 400:
  show the field in the LIST schema of the route (`fields`), add the reverse relation it
  goes through (`SchemaFields(include={'bookings': None})`), and list the search fields in
  `search_fields` (a route without them had a search over all text fields).
- A filter through a relation reaches the fields of the LIST schema of the default route
  of the related model: a field it hides cannot be filtered through the relation either.
- `BS_BAZIS_FILTERS_STRICT=false` restores the unrestricted filter, sorting and search of
  2.8 for a transition (`bazis.W006` warns). It is transitional and will be removed in a
  next release.
- bazis-permit: until its routes override `query_fields`, the scope of a permit route is
  its LIST schema without the field permissions (a field the permissions hide from a user
  is still reachable by the filter of the route itself; the relations into the objects of
  a permit model are restricted by its `restrict_queryset`). The override gives the union
  of the fields of the field groups of the user (`perms_field_groups`, the unpatched schema
  if an object can match none): a field always hidden from the user is cut, and the answer
  does not tell which right a user has. A field visible in some objects of the list only
  stays reachable for all of them.
- bazis-statusy: `status_aggs` applies the filter of the request with the deprecated
  `Filtering.qs_apply`, which is not restricted; apply it with
  `self.inject.filtering.apply(...)` (the scope of the route).
- bazis-front: the relation picker searches the related resource with `search=`; a route
  without `search_fields` answers 400, so give the routes the pickers search
  `search_fields`.
