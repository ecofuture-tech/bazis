# Bazis 2.10.0

## Features

- **One check of the invariants of an item for every way of writing it:
  `JsonApiMixin.validate_item(changes)`.** A rule about an item (a booking must not
  overlap another booking of its room, a limit of participants) was kept in the hooks of
  a route (`hook_before_create`, `hook_after_update`), and the relationships endpoints,
  the transits of bazis-statusy, the admin and `save()` bypassed it: a
  `PATCH /{item_id}/relationships/room/` moved a booking onto a taken room. A model now
  overrides `validate_item(self, changes)` and raises a Django `ValidationError` (a dict
  by field). The core calls it once per write of the item, after the values and the
  many-to-many relations are in the database and before the commit, in the same
  transaction (a query or `select_for_update` sees the write; a failure rolls it back):
  - the create, update and relationships endpoints of the routes, once at the end of the
    request, the included items each once;
  - the transits of bazis-statusy: from bazis-statusy 2.6.0 once per transit, source
    `transit` (before it each save of the transit is validated as a `save`);
  - any other `save()` and any change of a many-to-many relation through a manager (the
    admin, scripts, commands, background tasks), on both sides of the relation; `set()`
    (also `save_m2m()` of a form) once, on the final state.

  `changes` (`bazis.core.item_validation.ItemChanges`) has `fields` (the attributes and
  foreign keys whose values the write changed; all of them for a new item; without the
  `auto_now` timestamps), `relations` (the to-many and reverse relations set), `is_new`,
  `source` (`create`, `update`, `relationships`, `transit`, `save`) and `user` (of the
  route, the transit or the admin request; None in a script); in a block the source and
  the user of the outermost declaration win (a transit made in a hook of a create
  reports `create`). On the API a failure is 422 `ERR_ITEM_INVALID` with the pointer
  `/data/attributes/<field>`, `/data/relationships/<field>` or `/data`, under
  `/included/<index>` for an included item (on the relationships endpoints the parameter
  `/related_field_name`); elsewhere the save raises
  `bazis.core.errors.JsonApiItemInvalidException` (a `JsonApiBazisException` with the
  Django error in `error`) and rolls back only itself (a savepoint). The block
  `bazis.core.item_validation.defer_validate_item(user=...)` validates the writes of a
  script once at its end (an item written again after `scope.validate()` is validated
  again), and `bazis.core.admin_abstract.ValidateItemAdminMixin` does it for the change
  form of the admin (after the many-to-many relations and the inlines) and shows the
  errors in the form.

  The hooks stay for the side effects of the writes of a route. Not validated:
  `QuerySet.update()`, `bulk_create()`, `bulk_update()`, a reverse foreign key manager
  with `bulk=True` outside the routes, the rows of a `through` model written directly
  (`Through.objects.create()`), `loaddata`, raw SQL and deletion. A many-to-many
  `add()`, `remove()` or `clear()` writes without a savepoint: when its validation fails
  inside a transaction, the transaction (or the enclosing `atomic()` block) must be rolled
  back. A model that does not override `validate_item` pays nothing: no snapshot of its
  values, no savepoint, no receiver of `m2m_changed` (which would make Django query the
  targets of every `add()`), its managers unchanged.

## Changes

- **The routes link the items of a reverse foreign key one by one when their model
  overrides `validate_item`** (the relationships endpoints, an update and a create that
  set a reverse relation): each linked or unlinked item is saved with
  `save(update_fields=[<foreign key>])`, so that it is validated; before, and still for
  the other models, the manager wrote them with one `UPDATE`. Such a save writes only
  the foreign key (not the other columns, not `auto_now` fields) and sends `pre_save` and
  `post_save` for each item, with `update_fields`.
