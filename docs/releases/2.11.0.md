# Bazis 2.11.0

## Security

- **No route shows an item past its schema: `GET /{item_id}/dict_data/` is removed from
  `JsonapiRouteBase`.** Every route class had it, and it answered all the attributes of the
  model (`JsonApiMixin.dict_data`), whatever the `fields` of the route: a projection that
  hides fields, the field permissions of bazis-permit. It was an internal tool with no
  consumer in the framework; bazis-users already limited its own copy to staff
  (`UserRouteBase.action_dict_data`, unchanged by this release). The property
  `JsonApiMixin.dict_data` stays for the code of a project. A project that needs such a
  route defines it in its route class and restricts it itself:

  ```python
  @http_get('/{item_id}/dict_data/')
  def action_dict_data(self, item_id: str, **kwargs):
      if not self.inject.user.is_superuser:  # with bazis-users
          raise JsonApi403Exception()
      return self.set_item(item_id).dict_data
  ```

## Breaking changes

- **The errors of the request schemas (`ERR_VALIDATE`) point into the request document,
  as the errors of `validate_item` (`ERR_ITEM_INVALID`) and of the relation access
  (`ERR_RELATION_ACCESS`) do**: `/data/attributes/<field>`, `/data/relationships/<field>`,
  `/data/id`, and `/included/<index>/attributes/<field>` (`/relationships/<field>`) for
  the included item at that index. When the document gives the id of the item (an update,
  an included item to change), `source.id` and `source.type` name it. They were meant to,
  but `model_validate` (`bazis.core.schemas.validators`) changed the errors of one call of
  `ValidationError.errors()` and raised the fresh ones of another: the errors of the item
  and of every included item all pointed to `/attributes/<field>`, without the id, so the
  error of an included item could not be told from the error of the primary one. A client
  that maps the errors to the fields by `source.pointer` must read `/data/attributes/<f>`
  (and `/included/<i>/...`); during a transition it can accept both. On the relationships
  endpoints an error of the update schema points as in an update,
  `/data/relationships/<field>/...`, as `ERR_RELATION_ACCESS` does there.
- **`/{item_id}/dict_data/` is gone** (see Security): a request to it is 404.

## Fixes

- **The errors of writing an included item point to it.** `ERR_RELATION_ACCESS` of a
  relationship of an included item (and any error of its write that points to the item,
  `/data/...`, also from the hooks) pointed to `/data/relationships/<field>`, as if the
  primary item was wrong; it points to `/included/<index>/relationships/<field>` now.
- **A route class of a proxy model no longer changes the `actions_exclude` of its parent
  class.** It excluded create and update by extending the list it inherited, so a
  non-abstract sibling route class with the same parent lost create and update, and each
  subclass of a proxy route added them once more. It gets a list of its own now.

## Upgrading

- A client that shows the errors by field (the generated clients of bazis-front included)
  reads the pointers above.
- bazis-bulk passes the responses of the sub-requests through unchanged; its tests expect
  the new pointers and require this release for the tests only.
