# Bazis 2.12.0

## Security

- **`included` of a relation without a reverse one (`related_name='+'`) showed the
  related object of another item.** `included` of a forward foreign key or one-to-one
  relation queried the related objects by the name of the reverse relation, which is `+`
  for every relation declared without one: Django resolved it to the hidden reverse
  relation of whichever such relation to that model it registered (possibly of another
  model), so the query read `<related> JOIN <other model> ... WHERE <other model>.pk =
  <item pk>`. With UUID keys it found nothing (`include=attachment` was always empty, the
  symptom seen in a project); with integer keys (or keys shared between tables) it showed
  in `included` the related object of the other model's item with the same key (the file
  of note 5 in the `included` of ticket 5), with the attributes of the included schema.
  Only the `restrict_queryset` of the default route of the related model (and the
  permissions of bazis-permit on it) limited it; the identifiers in `relationships` were
  right. Every version up to 2.11.0 is affected. The related objects are now queried by
  the value of the foreign key of the item (`RelationInfo.get_child_queryset`); the
  many-to-many relations and the reverse relations were not affected. Projects with
  integer keys and relations with `related_name='+'` should upgrade.
- The filter by the objects of a model (`filter=crm.customer=<id>`) through such a relation
  filtered by the same hidden relation when the queries are not restricted
  (`BAZIS_FILTERS_STRICT=false`, `QueryToOrm` without a scope); with the strict queries
  (the default) it was refused. Such a relation does not filter now: the model is not
  related through it (400 `ERR_FILTER`, `ValueError` in `QueryToOrm`).

## Breaking changes

- **A create or an update that names an attribute or a relationship that is not in the
  schema of the route is 422 `ERR_VALIDATE`** (title `extra_forbidden`, pointer
  `/data/attributes/<f>`, `/data/relationships/<f>`, `/included/<i>/...`). It was answered
  200/201 and the field was left out silently, so a client could not tell a field excluded
  by `fields`, hidden by a field permission of bazis-permit (`disable`) or misspelled from
  a field that was written. A field that is in the schema but read-only there (a
  calculated field, `SchemaField(read_only=True)`, the permission `readonly`) is still
  ignored. The relationships endpoints keep answering a relationship that is not in the
  update schema with 403 `ERR_RELATIONSHIP_READONLY`. The request schemas of the create
  and the update have `additionalProperties: false` in the OpenAPI. The forms of
  bazis-front send only the fields of `schema_create/`/`schema_update/` of the user that
  are not read-only.
- **A text field (`CharField`, `TextField`) without `blank=True` refuses an empty value or
  one of only whitespace in a create or an update** (422 `ERR_VALIDATE` `Can't be blank` at
  the field), as the forms of Django and the admin do. The API wrote it: projects checked
  it in `validate_item`. The value is stored as sent (not stripped). A field the client
  may leave empty is `blank=True`; the request schemas show `"blank": false` for the
  others. The responses are no longer checked for blank values (also not for the
  `notblank` field permission of bazis-permit): a blank value in the database (written by
  code) no longer fails the response of an update.
- **`include` of a relation that is not in the schema of the action is 400 `ERR_INCLUDE`**
  (pointer `/query/include`, title `Invalid include`), as JSON:API requires for a path the
  server cannot include: a reverse relation not added to `fields`, an attribute, a path
  `a.b` (the core includes one level). It was left out silently (also for a user who could
  see the relation, such as `include=replies` of a route without `replies` in `fields`).
  An update accepts the relations of the update and of the create schema. A relation of
  the schema that a package hides from the user (the field permission `disable` of
  bazis-permit) is left out without an error. `BS_BAZIS_FILTERS_STRICT=false` (the
  transitional rollback of the strict queries) also restores the silent omission.
- The SQL of `included` for a forward relation is `WHERE <related>.pk IN (SELECT <fk> FROM
  <item table> WHERE id = ...)` instead of a join (tests that compare the SQL change).

## Fixes

- **An aggregate calculated field over a model with `Meta.ordering` failed** (`column ...
  must appear in the GROUP BY clause`): `FieldSubAggr` and `FieldDynamic(func=...)` kept
  the ordering of the related model in their subquery. They drop it now; a project no
  longer has to remove the ordering of the counted model.
- **The details of `ERR_FILTER` follow the language of the request** (`ru` is translated),
  as its title did: an unknown field, a lookup that a field does not support, a filter by
  objects or `$search` with a lookup, a route without search. The names and the values in
  them are given as they are; the messages of Django and Python (a value that is not a
  number) stay English.

## Features

- **Translated reference data: a `TranslatedField` (django-translated-fields, a dependency
  of the core) filters, sorts and searches by its column of the language of the
  request.** A `TranslatedFieldWithFallback(models.CharField(...), languages=[...])` was
  already one read-only attribute of the API in the language of the request, but it was
  not a key of `filter` or `sort` and the search could not use it: projects wrote a column
  per language and a calculated name by hand. It is now a field of the LIST schema that
  filters (`filterLabel`) and sorts (`orderLabel`), `search_fields = ['name']` searches it,
  `route_filter_fields/` lists it as a string, and `translated_name(model, name)`
  (`bazis.core.utils.query_complex`) gives the column for a query of a project. A blank
  translation is matched and sorted as empty (the fallback value is not in the column).
  The guide has the recipe.

## Guide

- The guide of the core (`bazis/core/AGENTS.md`) describes the calculated fields
  (`calc_property` with `FieldAnnotate` and `FieldDynamic`, aggregates, `as_filter`, adding
  them to the schema of a route), the numbers of `UniqNumberMixin` (django-sequences is
  installed by the core), the translated reference data, who calls `restrict_queryset`, a
  report on a proxy model, `ERR_INCLUDE` and the refused fields of a write; the sample
  project has an app `catalog` with these recipes and their tests.

## Upgrading

- A client that sends fields it does not know the route accepts (a generic form, the
  attributes of a response sent back) sends only the fields of `schema_create/` or
  `schema_update/`, without the read-only ones.
- Mark `blank=True` the text fields a client may leave empty; the checks of
  `validate_item` that refused an empty text of a `blank=False` field can be removed (keep
  them for the writes of code: `save()` does not run the schemas).
- Check the `include` parameters of the clients against the `fields` of the routes; add
  the reverse relations they include to `fields`.
- A project with integer keys and `related_name='+'` relations included in responses:
  review what the `included` of such relations showed (see Security).
